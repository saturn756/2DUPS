# 单模态 2D 感知系统 · 架构设计与规划

本文件夹是**架构骨架**：只定义「每个模块负责什么、模块之间传什么、有哪些硬约束」，**不涉及具体实现**（算法、模型、阈值、数据集版本都不在这里定）。实现选型在实施阶段逐项填入，并以决策记录的形式追加。

## 为什么要先做骨架

- **接口先于实现**：模块之间只依赖接口。换实现不改接口，下游就无需改动。
- **职责先于技术**：先把「谁负责什么、不负责什么」划清，避免后期因为职责重叠而返工。
- **骨架稳定、实现可变**：实现会随实验结论变化，骨架（职责 + 接口 + 约束）应当尽量稳定。
- **可独立评测**：每个模块都要有独立的验收维度，否则无法定位问题。

## 模块一览（骨架）

| 模块 | 职责 | 通路 |
|---|---|---|
| M1 采集与相机标定 | 统一坐标系与标定状态 | 基础 |
| M2 图像预处理与质量评价 | 图像版本与质量门控 | 基础 |

| M5 语义分割 | 像素级区域结构 | 结构 |
| M6 场景理解与拓扑推理 | 融合轨迹、区域与几何证据，输出结构化场景 | 汇合 |

## 设计原则

| 编号 | 原则 | 含义 |
|---|---|---|
| P1 | 接口先行，实现可替换 | 模块之间只通过本文档定义的接口通信；替换实现不得改变接口 |
| P2 | 只传结构化结果 | 不传递高维特征张量，避免下游与上游实现强绑定 |
| P3 | 失败必须显式 | 用状态字段表达「不可用 / 不可靠 / 降级」，不允许用默认值掩盖 |
| P4 | 可选输入缺失时降级 | 下游在缺少可选输入时给出降级结果，而不是猜测或崩溃 |
| P5 | 每模块可独立评测 | 每个模块有独立的验收维度与数据切片 |
| P6 | 语义与几何分离 | 语义结果（检测、分割）与几何结果（帧间变换、标定）分开产出，互不替代 |

## 阅读顺序

1. 先看 `../figures/图1-1_单模态2D感知系统架构.png`（模块功能与数据流）；需要边与接口细节时看 `../figures/图1-2_数据流与连接图.png`；
2. 再看 `01_系统架构.md` 了解范围与模块划分依据；
3. 再看 `03_数据流与连接逻辑.md`，理解模块之间怎么连、缺了会怎样；
4. 做实现时查 `02_模块规范.md` 与 `04_接口规范.md`；
5. 排期与填坑看 `05_实施规划.md`。

## 文档之间的依赖（改哪份）

```
01_系统架构 ── 定模块与边界
     │
02_模块规范 ── 定每个模块的职责、输入输出与约束
     │
03_数据流与连接逻辑 ── 定边、顺序、对齐与失败传播   ← 连接变了先改这里
     │
04_接口规范 ── 由连接推导出字段与不变量
     │
05_实施规划 ── 定怎么把实现填进来
```

改动顺序规则：**模块职责变 → 先改 01/02；连接变 → 先改 03；字段变 → 改 04**。图与下游材料在对应步骤后同步。

## 与阶段一材料的关系

阶段一《文献调研报告》《架构决策文档》与「图 1-1」是本骨架的**一次实例化**：它们在图 1-1 上标注了具体模型与指标。本文件夹是**不含实现的上位版本**；两者模块划分、数据流与接口保持一致，但本文件夹是后续修改架构的入口——**先改这里，再同步到图 1-1 与两份文档**。
